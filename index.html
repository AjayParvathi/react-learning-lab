Project Setup

Everything you need to go from zero to a running React app. Start here before writing any React code.

Step 1 — Install Node.js
React runs on Node.js. Download the LTS version from nodejs.org. Node comes with npm, the package manager you'll use every day.
node --version    # should be v18 or higher (v22 recommended)
npm --version     # should be v9 or higher
Step 2 — Create a project with Vite
Vite is the modern build tool the React team recommends. It starts in under 1 second. Create React App (CRA) is deprecated — don't start new projects with it.
# JavaScript project
npm create vite@latest my-app -- --template react
cd my-app && npm install && npm run dev

# TypeScript project (recommended for real apps)
npm create vite@latest my-app -- --template react-ts
Vite starts in ~300ms. CRA took 30+ seconds. Same React, just a much faster toolchain.

JSX

JSX (JavaScript XML) is a syntax extension for JavaScript that lets you write HTML-like code inside JavaScript files. It is not HTML — it compiles to React.createElement() function calls. JSX makes it intuitive to describe what the UI should look like alongside the logic that drives it.

You write
const el = <h1>Hello!</h1>
React compiles to
const el = React.createElement(
  'h1', null, 'Hello!'
)
▸ The mental model — JSX is just function calls
Think of JSX as a shorthand for creating UI descriptions. It is not HTML, not a template language, and not magic. Every JSX tag is a call to React.createElement which returns a plain JavaScript object — a description of what to render.

This means JSX follows JavaScript rules, not HTML rules. Anything that is valid in a JavaScript expression can go inside { }. Anything that is not an expression (statements like if/for) must be replaced with expression equivalents (ternary, &&, .map()).

Components & Props

A component is a self-contained, reusable piece of UI. In React, components are JavaScript functions that receive data (called props) and return JSX describing what should appear on screen. Your entire app is a tree of components — from the root App down to individual buttons.

Function declaration
function Welcome({ name }) {
  return <h1>Hi, {name}!</h1>
}
Arrow function
const Welcome = ({ name }) => (
  <h1>Hi, {name}!</h1>
)
Props — passing data in
<Welcome name="Aj" />
<Button label="Submit" color="blue" size={16} disabled={false} />

// Default prop values
const Button = ({ label = 'Click me', color = 'blue', disabled = false }) => (
  <button style={{ color }} disabled={disabled}>{label}</button>
)
The children prop
Anything placed between opening and closing tags becomes children. Used for wrapper components like cards, modals, layouts.
const Card = ({ children, title }) => (
  <div className="card">
    {title && <h2>{title}</h2>}
    {children}
  </div>
)

// Usage
<Card title="Profile">
  <img src="avatar.jpg" alt="avatar" />
  <p>Hello from inside the card!</p>
</Card>
Rendering lists
Use .map() to turn an array into JSX. The key prop must be a stable, unique ID — not the array index when items can be reordered or deleted.
const users = [
  { id: 1, name: 'Aj', role: 'Admin' },
  { id: 2, name: 'Sam', role: 'User' },
]

const UserList = () => (
  <ul>
    {users.map(user => (
      <li key={user.id}>{user.name} — {user.role}</li>
    ))}
  </ul>
)
Never use array index as key if the list can be filtered, sorted, or have items added/removed. Use a real unique ID.
Conditional rendering
// Ternary — show one of two things
{isLoggedIn ? <Dashboard /> : <Login />}

// Short-circuit — show something or nothing
{hasNotifications && <Badge count={5} />}

// Early return — cleanest for complex conditions
const UserCard = ({ user }) => {
  if (!user) return <p>No user found</p>
  if (user.banned) return <p>Account suspended</p>
  return <div>{user.name}</div>
}
▸ Pure components & immutability — never mutate state directly
A pure component always returns the same output for the same input — no side effects, no mutations. React components should be pure: given the same props and state, return the same JSX.

Immutability is the rule: never modify state directly. React uses reference equality (===) to detect changes. If you mutate an object in place, the reference stays the same, React sees no change, and the UI never updates.
// WRONG — mutating state directly (most common beginner bug)
const addItem = () => {
  items.push(newItem)      // mutates the array — same reference!
  setItems(items)          // React: "same array, no change" → no re-render
}

const updateUser = () => {
  user.name = 'Aj'         // mutates the object — same reference!
  setUser(user)            // React: "same object, no change" → no re-render
}

// CORRECT — always create a new value
const addItem    = () => setItems(prev => [...prev, newItem])
const removeItem = (id) => setItems(prev => prev.filter(i => i.id !== id))
const updateItem = (id, changes) => setItems(prev =>
  prev.map(i => i.id === id ? { ...i, ...changes } : i)
)
const updateUser = () => setUser(prev => ({ ...prev, name: 'Aj' }))

// Nested objects — must spread every level that changes
const updateCity = (city) => setUser(prev => ({
  ...prev,
  address: { ...prev.address, city }  // new nested object too
}))
Mutating state is the #1 cause of "my component didn’t update" bugs. Always return a new array/object.
▸ Lifting state up — share state between sibling components
When two sibling components need to share data, move the state to their closest common parent and pass it down as props. This is called lifting state up — one of the most important React patterns.
// PROBLEM — siblings can't share state with each other
const SearchInput = () => {
  const [query, setQuery] = useState('')
  // FilterList also needs query, but it's a sibling, not a child
}
const FilterList = () => { /* can't access SearchInput's query */ }

// SOLUTION — lift state to the closest common parent
const SearchPage = () => {
  const [query, setQuery] = useState('')  // lifted here

  return (
    <div>
      <SearchInput query={query} onQueryChange={setQuery} />
      <FilterList  query={query} />
    </div>
  )
}

const SearchInput = ({ query, onQueryChange }) => (
  <input value={query} onChange={e => onQueryChange(e.target.value)} />
)
const FilterList = ({ query }) => {
  const results = items.filter(i => i.name.toLowerCase().includes(query.toLowerCase()))
  return <ul>{results.map(i => <li key={i.id}>{i.name}</li>)}</ul>
}
Lift state only as high as needed — not all the way to a global store. If only 2 siblings need it, a shared parent is enough.
Prop spreading — passing many props at once
// Instead of writing each prop manually, spread them
const inputProps = {
  type: 'email', placeholder: 'Email', required: true
}
<input {...inputProps} />

// Very useful in wrapper components
const MyInput = ({ label, ...rest }) => (
  <div>
    <label>{label}</label>
    <input {...rest} />  {/* passes all remaining props */}
  </div>
)

Events

Events are how your UI responds to user actions — clicks, typing, form submissions, scrolling. React wraps browser events in a SyntheticEvent system that normalises behaviour across all browsers. Event handlers are camelCase in React (onClick, not onclick) and receive a function reference — not a string like in raw HTML.

Always pass a reference — not a call
const Button = () => {
  const handleClick = () => console.log('clicked!')

  return (
    <>
      <button onClick={handleClick}>OK</button>      {/* correct */}
      <button onClick={handleClick()}>Bad</button>   {/* runs on render! */}
    </>
  )
}
Passing arguments — wrap in an arrow function
const List = ({ users }) => {
  const handleDelete = (id, name) => {
    console.log(`Delete ${name} (id: ${id})`)
  }

  return (
    <ul>
      {users.map(u => (
        <li key={u.id}>
          {u.name}
          <button onClick={() => handleDelete(u.id, u.name)}>Delete</button>
        </li>
      ))}
    </ul>
  )
}
The event object
const handleChange  = (e) => console.log(e.target.value)   // input value
const handleSubmit  = (e) => { e.preventDefault(); submit() }
const handleKeyDown = (e) => { if (e.key === 'Enter') submit() }
const handleCheck   = (e) => console.log(e.target.checked)  // checkbox
▸ Event bubbling & stopPropagation
Events bubble up through the DOM — when you click a button inside a div, both the button’s and div’s click handlers fire. Sometimes you want to stop this.
const Card = () => {
  const handleCardClick = () => console.log('Card clicked')
  const handleButtonClick = (e) => {
    e.stopPropagation()    // stops event from bubbling to Card
    console.log('Button clicked only')
  }

  return (
    <div onClick={handleCardClick}>    {/* fires on any click inside */}
      <h2>Title</h2>
      <button onClick={handleButtonClick}>
        Click Me (won't trigger card)
      </button>
    </div>
  )
}

// e.preventDefault() — stop default browser behaviour
const Link = () => (
  <a href="/somewhere" onClick={(e) => {
    e.preventDefault()   // stop browser navigation
    console.log('Intercepted!')
  }}>Click</a>
)

// Keyboard events — detect specific keys
const SearchBox = () => (
  <input
    onKeyDown={(e) => {
      if (e.key === 'Enter')  submitSearch()
      if (e.key === 'Escape') clearSearch()
      if (e.ctrlKey && e.key === 'k') openCommandPalette()
    }}
  />
)

All React Hooks

Hooks are special functions that start with use and let you add React features (state, side effects, context, refs) to function components. Before hooks (pre-2019), you needed class components for these features. Hooks must always be called at the top level of a component — never inside loops, conditions, or nested functions — so React can track them in the same order every render.

▸ Stale closures — the most common hook bug
A stale closure happens when a function "captures" an old value of a variable and never sees updates. This is the #1 confusing bug beginners hit with useEffect and useCallback.
// BUG — stale closure
const Counter = () => {
  const [count, setCount] = useState(0)

  useEffect(() => {
    const interval = setInterval(() => {
      console.log(count)     // always logs 0 — captures the initial value!
      setCount(count + 1)    // always sets to 0 + 1 = 1, never increments
    }, 1000)
    return () => clearInterval(interval)
  }, [])  // empty deps = effect never re-runs = count is forever 0 inside

  return <p>{count}</p>
}

// FIX 1: add count to dependency array — re-creates interval when count changes
useEffect(() => {
  const interval = setInterval(() => setCount(count + 1), 1000)
  return () => clearInterval(interval)
}, [count])

// FIX 2: use the updater function — doesn't need to "see" current count
useEffect(() => {
  const interval = setInterval(() => setCount(prev => prev + 1), 1000)
  return () => clearInterval(interval)
}, [])  // safe — updater function always gets fresh value
Rule of thumb: whenever you use state inside useEffect, use the prev => prev + 1 updater form, or add the value to the dependency array. ESLint’s exhaustive-deps rule catches stale closures automatically.
▸ Automatic batching — React 18 groups state updates
Batching means React groups multiple setState calls into a single re-render. Before React 18, batching only worked inside React event handlers. In React 18+, it works everywhere — inside timeouts, promises, and async functions too.
// React 18 — automatic batching everywhere
const handleClick = async () => {
  setLoading(true)
  setError(null)
  setData(null)
  // React 18: one re-render (batched), not three
}

setTimeout(() => {
  setCount(c => c + 1)
  setName('Aj')
  // React 18: one re-render (batched)
  // React 17: two separate re-renders
}, 1000)

// Force immediate re-render between updates (rare — avoid this)
import { flushSync } from 'react-dom'
flushSync(() => setCount(c => c + 1))   // renders immediately
flushSync(() => setName('Aj'))           // renders immediately
// Use flushSync only for third-party integrations that need sync DOM updates
State

useState — store a changing value

The most used hook. When state changes, the component re-renders.

▶
Analogy: a sticky note React watches
import { useState } from 'react'

const Counter = () => {
  const [count, setCount] = useState(0)
  //     ^ value   ^ setter  ^ initial value

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(prev => prev + 1)}>+</button>
      <button onClick={() => setCount(0)}>Reset</button>
    </div>
  )
}

// Object in state — always spread, never mutate directly
const [user, setUser] = useState({ name: '', email: '' })
setUser(prev => ({ ...prev, name: 'Aj' }))
Use prev => prev + 1 (function form) when the new value depends on the old one. Safe even when React batches updates.

useReducer — complex state logic

Like useState but centralises all update logic in one reducer function. Great for 3+ related state values.

▶
import { useReducer } from 'react'

const reducer = (state, action) => {
  switch (action.type) {
    case 'increment': return { ...state, count: state.count + 1 }
    case 'decrement': return { ...state, count: state.count - 1 }
    case 'reset':     return { count: 0 }
    case 'setTo':     return { count: action.payload }
    default: throw new Error('Unknown action: ' + action.type)
  }
}

const Counter = () => {
  const [state, dispatch] = useReducer(reducer, { count: 0 })

  return (
    <div>
      <p>{state.count}</p>
      <button onClick={() => dispatch({ type: 'increment' })}>+</button>
      <button onClick={() => dispatch({ type: 'setTo', payload: 10 })}>Set 10</button>
    </div>
  )
}
Refs

useRef — access DOM or store a silent value

Holds a value that persists across renders but does NOT trigger re-render when changed.

▶
import { useRef, useEffect } from 'react'

// Use 1: Access a DOM element directly
const AutoFocus = () => {
  const inputRef = useRef(null)
  useEffect(() => { inputRef.current.focus() }, [])
  return <input ref={inputRef} placeholder="Auto-focused!" />
}

// Use 2: Store a value without re-rendering
// Perfect for: timer IDs, previous values, render counts
const Timer = () => {
  const intervalRef = useRef(null)
  const start = () => { intervalRef.current = setInterval(() => console.log('tick'), 1000) }
  const stop  = () => clearInterval(intervalRef.current)
  return <><button onClick={start}>Start</button><button onClick={stop}>Stop</button></>
}

useImperativeHandle — choose what ref exposes

Controls which methods a parent can call on a child via ref.

▶
import { useRef, useImperativeHandle } from 'react'

// React 19 — ref is a regular prop (no forwardRef needed)
const FancyInput = ({ ref, ...props }) => {
  const inputRef = useRef()

  useImperativeHandle(ref, () => ({
    focus:    () => inputRef.current.focus(),
    clear:    () => { inputRef.current.value = '' },
    getValue: () => inputRef.current.value,
  }))

  return <input ref={inputRef} {...props} />
}

const Parent = () => {
  const ref = useRef()
  return (
    <div>
      <FancyInput ref={ref} />
      <button onClick={() => ref.current.focus()}>Focus</button>
      <button onClick={() => ref.current.clear()}>Clear</button>
    </div>
  )
}
In React 19, ref is a regular prop. The old forwardRef() wrapper is no longer needed.
Effects

useEffect — run code after render

For side effects: fetching data, subscriptions, timers, DOM manipulation.

▶
import { useEffect, useState } from 'react'

const UserList = () => {
  const [users, setUsers] = useState([])

  useEffect(() => {
    // Define async inside the effect — can't make the effect itself async
    const fetchUsers = async () => {
      const res  = await fetch('/api/users')
      const data = await res.json()
      setUsers(data)
    }
    fetchUsers()
  }, [])   // [] = run only once when component mounts

  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>
}
Dependency arrayWhen it runs
OmittedAfter every render
[] emptyOnce on mount
[id]On mount + when id changes
// Cleanup — return a function to clean up before next run or unmount
useEffect(() => {
  const sub = subscribeToEvents(userId, handler)
  return () => sub.unsubscribe()
}, [userId])
Always clean up subscriptions, event listeners, and timers. Missing cleanup causes memory leaks.
// WHAT HAPPENS TIMELINE:
// 1. Component mounts          → effect runs  → starts subscription/timer
// 2. Dependency changes        → cleanup runs → stops old subscription
//                              → effect runs  → starts new subscription  
// 3. Component unmounts        → cleanup runs → stops subscription

// MEMORY LEAK — missing cleanup
useEffect(() => {
  window.addEventListener('resize', handler)
  // nothing returned — handler NEVER removed — leak!
}, [])

// CORRECT — cleanup removes the listener
useEffect(() => {
  window.addEventListener('resize', handler)
  return () => window.removeEventListener('resize', handler)
}, [])

useLayoutEffect — run before browser paints

Same as useEffect but fires synchronously after DOM updates. Use only when measuring DOM size/position.

▶
import { useLayoutEffect, useRef, useState } from 'react'

const Tooltip = ({ children }) => {
  const ref = useRef()
  const [height, setHeight] = useState(0)

  useLayoutEffect(() => {
    // Reads DOM before paint — no flicker
    setHeight(ref.current.getBoundingClientRect().height)
  }, [])

  return <div ref={ref}>{children} (height: {height}px)</div>
}
Use useEffect by default. Switch to useLayoutEffect only if you see visible flickering.
Performance

useMemo — cache an expensive calculation

Only recalculates when dependencies change. Skips the work on every other render.

▶
import { useMemo } from 'react'

const ProductList = ({ products, filterText, sortKey }) => {
  const filtered = useMemo(() => {
    return products
      .filter(p => p.name.toLowerCase().includes(filterText.toLowerCase()))
      .sort((a, b) => a[sortKey] > b[sortKey] ? 1 : -1)
  }, [products, filterText, sortKey])

  return <ul>{filtered.map(p => <li key={p.id}>{p.name}</li>)}</ul>
}
Only use useMemo for genuinely slow calculations. The React Compiler (React 19, opt-in) automates this — check the docs.

useCallback — cache a function reference

Returns the same function object between renders. Needed when passing functions to memoized children.

▶
import { useCallback, memo, useState } from 'react'

const Parent = () => {
  const [count, setCount] = useState(0)

  // Without useCallback: new function every render → Child re-renders unnecessarily
  // With useCallback: same reference → Child skips re-render
  const handleAction = useCallback((id) => {
    console.log('action on', id)
  }, [])   // no deps = never recreated

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>Count: {count}</button>
      <ExpensiveList onAction={handleAction} />
    </div>
  )
}

// memo() is required for useCallback to have any effect
const ExpensiveList = memo(({ onAction }) => (
  <li onClick={() => onAction(1)}>Item</li>
))
Context & Transitions (React 18+)

useContext — read context values

Reads the value from the nearest matching Provider above in the tree.

▶
import { createContext, useContext } from 'react'

const ThemeContext = createContext('light')

const App = () => (

Custom Hooks

Custom hooks are how you reuse stateful logic between components. Whenever you find yourself copying the same useState + useEffect pattern into multiple components, extract it into a custom hook. A custom hook is just a regular JavaScript function that starts with use and can call other hooks inside it. Unlike components, custom hooks return data — not JSX.

useFetch — reusable data loading
import { useState, useEffect, useCallback } from 'react'

const useFetch = (url) => {
  const [data, setData]       = useState(null)
  const [loading, setLoading] = useState(true)
  const [error, setError]     = useState(null)

  const fetchData = useCallback(async () => {
    try {
      setLoading(true); setError(null)
      const res = await fetch(url)
      if (!res.ok) throw new Error(`HTTP ${res.status}`)
      setData(await res.json())
    } catch (err) {
      setError(err.message)
    } finally {
      setLoading(false)
    }
  }, [url])

  useEffect(() => { fetchData() }, [fetchData])

  return { data, loading, error, refetch: fetchData }
}

// Usage
const UserPage = () => {
  const { data: users, loading, error, refetch } = useFetch('/api/users')

  if (loading) return <p>Loading...</p>
  if (error)   return <p>{error} <button onClick={refetch}>Retry</button></p>
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>
}

Context API

Context API is React's built-in solution for prop drilling — the problem of passing data through many layers of components just so a deeply nested component can access it. Context creates a "broadcast channel" at a high level in the tree; any descendant component can subscribe to it and read the value directly, skipping all the layers in between.

When to use Context vs Props
Use Context forKeep as Props for
Current authenticated userComponent-specific data
Theme (dark/light mode)Event handlers between parent and child
Language / locale preferenceAnything only 1–2 components need
Global feature flagsFrequently changing values (use a state library)
▸ Prop drilling — the problem Context solves
Prop drilling is passing data through multiple component layers just to get it to a deeply nested component that needs it. The middle components don’t use the data — they just pass it through.
// PROP DRILLING — username has to pass through 3 components that don't need it
const App = () => <Layout username="Aj" />
const Layout = ({ username }) => <Sidebar username={username} />    // doesn't use it
const Sidebar = ({ username }) => <NavLinks username={username} />  // doesn't use it
const NavLinks = ({ username }) => <p>Hi, {username}!</p>           // finally uses it

// WITH CONTEXT — NavLinks reads it directly, no drilling
const App = () => (
  <UserContext.Provider value={{ username: 'Aj' }}>
    <Layout />          {/* no props needed */}
  </UserContext.Provider>
)
const Layout  = () => <Sidebar />                    // no prop passing
const Sidebar = () => <NavLinks />                   // no prop passing
const NavLinks = () => {
  const { username } = useContext(UserContext)        // reads directly
  return <p>Hi, {username}!</p>
}
Prop drilling 2–3 levels deep is normal and fine. Context becomes useful when you’re drilling 4+ levels, or when many unrelated components need the same data.

// High-performance context pattern — separate state from dispatch
const CounterStateContext   = createContext(null)

    <CounterStateContext.Provider value={count}>
      <CounterDispatchContext.Provider value={dispatch}>
        {children}
      </CounterDispatchContext.Provider>

  )
}

Context best practices

Split by concern

One context for auth, one for theme, one for cart. A single giant AppContext is a mess.

2

3

Every consumer re-renders when context changes. Mouse position, scroll values → use useRef or Zustand instead.

▸ AbortController — cancel fetch requests on cleanup
When a component unmounts while a fetch is still running, React tries to update state that no longer exists. AbortController lets you cancel in-flight requests in the useEffect cleanup function.
// WITHOUT cleanup — causes React warning and potential bugs
useEffect(() => {
  fetch('/api/users')
    .then(r => r.json())
    .then(data => setUsers(data))  // may run after component unmounts!
}, [])

// WITH AbortController — cancels the request on unmount
useEffect(() => {
  const controller = new AbortController()

  const load = async () => {
    try {
      const res  = await fetch(`/api/users/${userId}`, {
        signal: controller.signal   // attach the abort signal
      })
      const data = await res.json()
      setUsers(data)
    } catch (err) {
      if (err.name === 'AbortError') return   // cancelled — not a real error, ignore
      setError(err.message)
    }
  }

  load()
  return () => controller.abort()  // cancel if userId changes or component unmounts
}, [userId])

// With axios — pass signal in config
useEffect(() => {
  const controller = new AbortController()
  api.get('/api/users', { signal: controller.signal })
    .then(r => setUsers(r.data))
    .catch(err => { if (!axios.isCancel(err)) setError(err.message) })

▸ Axios interceptors — handle auth & errors globally
Interceptors are functions that run automatically before every request or after every response. Use them to attach auth tokens and handle common errors (like 401 Unauthorized) in one place instead of in every API call.
// services/api.js — set this up once at app startup
import axios from 'axios'

  baseURL: import.meta.env.VITE_API_URL,
  timeout: 10000,
})

// REQUEST interceptor — runs before every request leaves
api.interceptors.request.use(
  (config) => {
    const token = localStorage.getItem('accessToken')
    if (token) {
      config.headers.Authorization = `Bearer ${token}`
    }
    return config       // must return the config
  },
  (error) => Promise.reject(error)
)

// RESPONSE interceptor — runs after every response arrives
api.interceptors.response.use(
  (response) => response,   // success — pass through unchanged

  async (error) => {
    const originalRequest = error.config

    // Token expired (401) — try to refresh it automatically
    if (error.response?.status === 401 && !originalRequest._retried) {
      originalRequest._retried = true       // prevent infinite loop
      try {
        const { data } = await axios.post('/api/auth/refresh')
        localStorage.setItem('accessToken', data.accessToken)
        originalRequest.headers.Authorization = `Bearer ${data.accessToken}`
        return api(originalRequest)         // retry the original request
      } catch {
        localStorage.removeItem('accessToken')
        window.location.href = '/login'     // refresh failed — force login
      }
    }

    // 403 — permission denied
    if (error.response?.status === 403) {
      console.error('Permission denied')
    }

    // 500 — server error — show toast
    if (error.response?.status >= 500) {
      showToast('Server error — please try again')
    }

    return Promise.reject(error)
  }
)
TanStack Query v5 (React Query) — server state management
What it is: TanStack Query is a library that manages server state — data that lives on a remote server and needs to be fetched, cached, and kept in sync with your UI. It completely replaces the manual useEffect + useState + loading + error pattern.

The core idea: You tell it what to fetch (a function) and when to consider data stale. It handles everything else — caching, background refetching, retries, deduplication across components, and window-focus refetching.
ConceptWhat it means
queryKeyA unique array identifying this query. Same key = shared cache. ['posts'], ['post', 5], ['posts', { status: 'published' }]
queryFnThe async function that fetches data. Must return a promise that resolves with the data.
staleTimeHow long (ms) cached data is considered fresh. No refetch during this window. Default: 0 (always stale).
gcTimeHow long unused cache stays in memory before garbage collection. Default: 5 minutes.
isLoadingTrue only on first fetch with no cached data. Show a full loading screen.
isFetchingTrue whenever a request is in-flight, including background refreshes. Show a subtle indicator.
invalidateQueriesMarks cached data as stale and triggers a background refetch on next access.
setQueryDataManually update the cache — instant UI update without a round-trip to the server.

Performance

React re-renders a component whenever its state or props change. For most apps, this is fast enough to never notice. Performance becomes an issue only when: (1) a component renders very frequently, (2) it does expensive work during render, or (3) it renders a huge number of items at once. Always profile first with React DevTools Profiler — fix what you can measure, not what you guess.

Patterns

Design patterns are proven, reusable solutions to recurring problems in software design. In React, patterns emerge from the constraints of component composition — how to share logic, expose flexible APIs, render into different DOM locations, and let parent components control child behaviour. Compound components — flexible component APIs

This is one of the most common TypeScript questions. The short answer: use interface for objects and component props. Use type for unions, intersections, and utility types. They can do most of the same things, so pick one convention and stay consistent.

// useFetch with generics — works with any data shape
const useFetch = <T>(url: string) => {
  const [data, setData]       = useState<T | null>(null)
  const [loading, setLoading] = useState(true)
  const [error, setError]     = useState<string | null>(null)

      .then(r => r.json() as Promise<T>)
      .then(data => { setData(data); setLoading(false) })
      .catch(err =>  { setError(err.message); setLoading(false) })

  return { data, loading, error }
}

State Management

State is any data that changes over time and causes your UI to update. Choosing the right tool depends entirely on what kind of state you're managing.

What is state management?
Every React app has state — from a simple boolean (is this modal open?) to complex server data (a list of orders from an API). "State management" is the pattern of deciding where state lives, how it changes, and who can access it.

The mistake most beginners make is reaching for Redux for everything. In reality, different types of state need different tools.
What is "state" in React?
State is any data in your app that changes over time and affects what is displayed on screen. Examples: whether a modal is open, the items in a shopping cart, the current user’s profile, search results from an API.

React state has two important properties: (1) when state changes, React automatically re-renders the affected components, and (2) state is owned — it lives in exactly one place and is passed down to children that need it.

The challenge is deciding where each piece of state should live. State that only one component needs stays local (useState). State that many components across the app need becomes global (Context, Zustand, Redux).

Zustand — lightweight global state
What it is: Zustand (German for "state") is a tiny, fast state manager for React. You define a store — an object containing state values and functions that update them — and any component can read or write to it without a Provider wrapper.

When to use it: When Context starts feeling clunky, when you need global state without Redux's boilerplate, or when you need state that multiple unrelated components share (shopping cart, notifications, user preferences).

Security Essentials

Security mistakes in React apps are mostly about trusting user input. Understanding the basics protects your users and keeps your app off the breach headlines.

▸ XSS — Cross-Site Scripting
XSS is when an attacker injects malicious JavaScript into your page that runs in other users’ browsers — stealing cookies, session tokens, or redirecting to phishing sites.

React is safe by default. All values inside JSX expressions ({value}) are automatically escaped — <script> tags become plain text, never executable code. The only danger is when you deliberately bypass this.
// SAFE — React escapes this automatically
const userInput = '<script>alert("hacked!")</script>'
return <p>{userInput}</p>
// Renders as literal text: <script>alert("hacked!")</script>

// DANGEROUS — bypasses React's protection
return <div dangerouslySetInnerHTML={{ __html: userInput }} />
// Actually runs the script! Only use with sanitised, trusted content
▸ dangerouslySetInnerHTML — the only escape hatch
Sometimes you genuinely need to render HTML strings — from a rich text editor, a CMS, or markdown renderer. dangerouslySetInnerHTML is the only way to do this. Always sanitise the HTML first.
// WRONG — render raw HTML from user or untrusted source
<div dangerouslySetInnerHTML={{ __html: rawHtml }} />

// CORRECT — sanitise first, then render
// npm install dompurify
import DOMPurify from 'dompurify'

const SafeHTML = ({ html }) => {
  const clean = DOMPurify.sanitize(html, {
    ALLOWED_TAGS:  ['p', 'b', 'i', 'em', 'strong', 'a', 'ul', 'ol', 'li'],
    ALLOWED_ATTR:  ['href', 'target'],
  })
  return <div dangerouslySetInnerHTML={{ __html: clean }} />
}

// Use cases where it's appropriate:
// - Rendering output from a trusted rich-text editor (Quill, TipTap)
// - Rendering sanitised markdown HTML
// - Embedding trusted CMS content
Never use dangerouslySetInnerHTML with user-generated content unless you sanitise it with DOMPurify first. One XSS vulnerability can compromise every user of your app.
▸ CORS — Cross-Origin Resource Sharing
CORS is a browser security mechanism. When your React app (on localhost:5173) makes a request to an API on a different domain (api.example.com), the browser blocks it unless the server explicitly allows it.

CORS is a server-side configuration — you cannot fix it from React. Your backend must send the right headers.
// You see this error in the browser console:
// "Access to fetch from origin 'http://localhost:5173' has been blocked by CORS policy"

// WRONG — you cannot fix CORS from React
fetch('https://api.example.com/users', {
  headers: { 'Access-Control-Allow-Origin': '*' },  // this does nothing — server must set it
})

// FIX 1: Configure your backend to send CORS headers (Node/Express)
// npm install cors
app.use(cors({ origin: 'http://localhost:5173' }))

// FIX 2: Proxy requests through Vite in development
// vite.config.js
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'https://api.example.com',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ''),
      }
    }
  }
})
// Now fetch('/api/users') → proxied to https://api.example.com/users
// No CORS because the request comes from the same origin

// FIX 3: In production, your frontend and backend should share a domain
// (e.g. both on api.yourapp.com) or use a reverse proxy (Nginx)

Virtual DOM & React Internals

The Virtual DOM is React's performance strategy. Directly manipulating the browser's real DOM is slow — every change can trigger expensive layout recalculations and repaints. Instead, React maintains a lightweight JavaScript copy of the DOM in memory. When state changes, React builds a new virtual copy, diffs it against the previous one to find exactly what changed, then applies only those minimal changes to the real DOM.

Why the Virtual DOM exists
Without React
// 1000 DOM writes
for (let i = 0; i < 1000; i++) {
  el.textContent = newValues[i]
}
// Each write can trigger reflow/repaint
// Very slow for large updates
With React
// React diffs old vs new Virtual DOM
// Computes the minimal set of changes
// Applies them in one batch to the DOM
setItems(newItems)
// Could be 1 DOM write instead of 1000
Reconciliation — how React decides what changed
1
Render phase

React calls your component functions and builds a new tree of JS objects (Virtual DOM). Fast — happens entirely in memory.

2
Diff phase

React compares new tree vs previous tree using a heuristic O(n) algorithm (not naïve O(n³)).

3
Commit phase

React applies only the minimal set of changes to the real DOM. This is the slow step — React minimises it.

The key prop — how React tracks list items
// Without key — React can't tell which item changed
{items.map(item => <li>{item.name}</li>)}

// Index as key — breaks when list is sorted, filtered, or modified
{items.map((item, i) => <li key={i}>{item.name}</li>)}

// Stable unique ID — correct
{items.map(item => <li key={item.id}>{item.name}</li>)}

// Intentional remount trick — change key to reset all state in a component
<UserProfile key={userId} />  // mounts fresh whenever userId changes
React Fiber — the engine behind React
React 16 rewrote the reconciler as "Fiber" — a linked-list structure that can pause, resume, and prioritise rendering work. This enables everything in modern React:

Redux Toolkit — Deep Dive

Redux Toolkit (RTK) is the official, opinionated way to write Redux logic. It eliminates boilerplate, enforces best practices, and bundles everything you need — state slices, async actions, the store, and even an API layer (RTK Query).

▸ What is Redux? Why does it exist?
Redux is a predictable state container. It enforces one rule: state can only change through dispatched actions processed by pure reducer functions. This single rule makes every state change traceable, testable, and replayable in DevTools.

React’s built-in tools (useState, Context) work well for UI state and moderate sharing. Redux becomes worthwhile when:
• Many unrelated components need the same data
• You need undo/redo or time-travel debugging
• A large team needs strict conventions around state
• State transitions are complex and need audit trails

▸ createSlice — the heart of RTK
createSlice bundles initial state, all reducer functions, and auto-generated action creators into one place. It uses Immer internally, so you can write “mutating” code safely — Immer converts it to immutable updates behind the scenes.
// features/cart/cartSlice.js
import { createSlice } from '@reduxjs/toolkit'

const cartSlice = createSlice({
  name: 'cart',                          // prefix for action types: 'cart/addItem'
  initialState: {
    items: [],
    coupon: null,
    isOpen: false,
  },

  reducers: {
    // Each key becomes an action creator automatically
    addItem(state, action) {
      const existing = state.items.find(i => i.id === action.payload.id)
      if (existing) {
        existing.quantity += 1           // Immer: "mutate" safely
      } else {
        state.items.push({ ...action.payload, quantity: 1 })
      }
    },

    removeItem(state, action) {
      state.items = state.items.filter(i => i.id !== action.payload)
    },

    updateQuantity(state, action) {
      const { id, quantity } = action.payload
      const item = state.items.find(i => i.id === id)
      if (item) item.quantity = Math.max(1, quantity)
    },

    clearCart(state) {
      state.items = []
      state.coupon = null
    },

    applyCoupon(state, action) {
      state.coupon = action.payload     // 'SAVE10', 'FLASH20', etc.
    },

    toggleCart(state) {
      state.isOpen = !state.isOpen
    },
  },
})

// Export action creators (auto-generated from reducer names)
export const {
  addItem,
  removeItem,
  updateQuantity,
  clearCart,
  applyCoupon,
  toggleCart,
} = cartSlice.actions

▸ createAsyncThunk — async actions (API calls)
createAsyncThunk wraps an async function and automatically dispatches pending, fulfilled, and rejected actions as the promise moves through its lifecycle. You handle these in extraReducers.
// features/products/productsSlice.js
import { createSlice, createAsyncThunk } from '@reduxjs/toolkit'
import { productService } from '../../services/productService'

// 1. Define the async thunk
export const fetchProducts = createAsyncThunk(
  'products/fetchAll',                     // action type prefix
  async (filters = {}, { rejectWithValue }) => {
    try {
      return await productService.getAll(filters)
    } catch (err) {
      // rejectWithValue sends a structured error to the rejected case
      return rejectWithValue(err.response?.data?.message || err.message)
    }
  }
)

export const fetchProductById = createAsyncThunk(
  'products/fetchOne',
  async (id, { rejectWithValue }) => {
    try {
      return await productService.getById(id)
    } catch (err) {
      return rejectWithValue(err.message)
    }
  }
)

export const createProduct = createAsyncThunk(
  'products/create',
  async (productData, { rejectWithValue }) => {
    try {
      return await productService.create(productData)
    } catch (err) {
      return rejectWithValue(err.message)
    }
  }
)

// 2. Create slice with extraReducers handling the thunk lifecycle
const productsSlice = createSlice({
  name: 'products',
  initialState: {
    list:      [],
    selected:  null,
    loading:   false,
    error:     null,
    filters:   { category: 'all', sort: 'name' },
  },
  reducers: {
    setFilter(state, action) {
      state.filters = { ...state.filters, ...action.payload }
    },
    clearSelected(state) {
      state.selected = null
    },
  },
  extraReducers: (builder) => {
    builder
      // fetchProducts
      .addCase(fetchProducts.pending, (state) => {
        state.loading = true
        state.error   = null
      })
      .addCase(fetchProducts.fulfilled, (state, action) => {
        state.loading = false
        state.list    = action.payload
      })
      .addCase(fetchProducts.rejected, (state, action) => {
        state.loading = false
        state.error   = action.payload    // the value from rejectWithValue
      })

      // fetchProductById
      .addCase(fetchProductById.pending,   (state) => { state.loading = true })
      .addCase(fetchProductById.fulfilled, (state, action) => {
        state.loading  = false
        state.selected = action.payload
      })
      .addCase(fetchProductById.rejected, (state, action) => {
        state.loading = false
        state.error   = action.payload
      })

      // createProduct — add to list on success
      .addCase(createProduct.fulfilled, (state, action) => {
        state.list.unshift(action.payload)
      })
  },
})

▸ RTK Query — data fetching built into RTK
RTK Query is a powerful data fetching and caching tool bundled with Redux Toolkit. Instead of writing thunks + slice reducers for every API endpoint, you define all endpoints in one createApi call and get auto-generated hooks. It handles caching, background refetching, and cache invalidation via a tag system.
// services/postsApi.js — define all endpoints once
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react'

export const postsApi = createApi({
  reducerPath: 'postsApi',       // key in the Redux store
  baseQuery: fetchBaseQuery({
    baseUrl: '/api',
    prepareHeaders: (headers) => {
      const token = localStorage.getItem('token')
      if (token) headers.set('Authorization', `Bearer ${token}`)
      return headers
    },
  }),
  tagTypes: ['Post', 'Comment'],  // cache tag categories

  endpoints: (builder) => ({

    // GET all posts
    getPosts: builder.query({
      query: (params = {}) => ({
        url: '/posts',
        params,                        // ?page=1&limit=10&category=react
      }),
      providesTags: (result) =>
        result
          ? [...result.map(({ id }) => ({ type: 'Post', id })), 'Post']
          : ['Post'],
    }),

    // GET one post
    getPost: builder.query({
      query: (id) => `/posts/${id}`,
      providesTags: (result, error, id) => [{ type: 'Post', id }],
    }),

    // CREATE — mutation
    createPost: builder.mutation({
      query: (body) => ({ url: '/posts', method: 'POST', body }),
      invalidatesTags: ['Post'],       // auto-refetch getPosts list
    }),

    // UPDATE — mutation
    updatePost: builder.mutation({
      query: ({ id, ...body }) => ({ url: `/posts/${id}`, method: 'PUT', body }),
      invalidatesTags: (result, error, { id }) => [{ type: 'Post', id }],
    }),

    // DELETE — mutation
    deletePost: builder.mutation({
      query: (id) => ({ url: `/posts/${id}`, method: 'DELETE' }),
      invalidatesTags: (result, error, id) => [{ type: 'Post', id }, 'Post'],
    }),

    // GET comments for a post
    getComments: builder.query({
      query: (postId) => `/posts/${postId}/comments`,
      providesTags: (result, error, postId) => [{ type: 'Comment', id: postId }],
    }),
  }),
})

TanStack Query is the industry standard for managing server state in React. It handles fetching, caching, synchronising, and updating data from remote sources — so you don’t have to.

▸ What problem does it solve?

▸ Optimistic Updates — instant UI, sync in background
Show the expected result before the server confirms it. If the server returns an error, automatically rollback. This makes apps feel instant — like native apps.
const LikeButton = ({ post }) => {
  const queryClient = useQueryClient()

  const likeMutation = useMutation({
    mutationFn: (postId) => fetch(`/api/posts/${postId}/like`, { method: 'POST' }),

    // 1. Before the mutation fires — update cache optimistically
    onMutate: async (postId) => {
      // Cancel any in-flight refetches that could overwrite optimistic update
      await queryClient.cancelQueries({ queryKey: ['post', postId] })

      // Snapshot the previous value (for rollback)
      const previous = queryClient.getQueryData(['post', postId])

      // Optimistically update the cache
      queryClient.setQueryData(['post', postId], (old) => ({
        ...old,
        likes:   (old?.likes ?? 0) + 1,
        liked:   true,
      }))

      return { previous, postId }   // context passed to onError
    },

    // 2. If mutation fails — rollback to snapshot
    onError: (err, postId, context) => {
      queryClient.setQueryData(['post', context.postId], context.previous)
      alert('Failed to like. Reverting.')
    },

    // 3. After success or error — sync with server
    onSettled: (data, error, postId) => {
      queryClient.invalidateQueries({ queryKey: ['post', postId] })
    },
  })

  return (
    <button onClick={() => likeMutation.mutate(post.id)}>
      {post.liked ? '❤ Liked' : '♡ Like'} ({post.likes})
    </button>
  )
}
The onMutate → onError → onSettled pattern is the standard for optimistic updates. onMutate optimistically changes the cache, onError rolls back if needed, onSettled always syncs the final state.

▸ React interview questions — what they really test
Interviewers rarely ask you to build a full app from scratch. They test whether you understand why React works the way it does. Here are the most common questions and what a strong answer sounds like:
QuestionWhat they want to hear
What is the Virtual DOM?React keeps a JS copy of the DOM, diffs it on state change, then applies only the minimum changes to the real DOM — avoiding expensive full-page repaints
What is reconciliation?The process of comparing old vs new virtual DOM and computing the minimal set of real DOM updates needed
Why do we need keys in lists?Keys help React identify which items changed, moved, or were added/removed — preventing wrong state being attached to the wrong element after reorder
What is a controlled component?An input whose value is controlled by React state — every keystroke calls setState, making React the single source of truth for the value
What is prop drilling?Passing props through intermediate components that don’t use them just to reach a deeply nested one — Context or state management libraries solve this
When would you use useCallback?When passing a function as a prop to a memoised child — without it, a new function reference is created each render, making memo() ineffective
What is a side effect?Anything a component does outside of returning JSX — fetching data, setting timers, subscribing to events, updating document.title. Handle with useEffect.
What is a stale closure?When a function inside useEffect captures an old value of state/props and never sees the updated value. Fixed with the updater form or correct dependency array.
Controlled vs uncontrolled?Controlled: React state owns the value (via value + onChange). Uncontrolled: DOM owns it, you read via ref. Use controlled for almost everything.
useState vs useReducer?useState for simple independent values. useReducer when you have 3+ related values or complex logic where next state depends on current state.
